# Теоретичні питання до захисту (короткі відповіді)

Відповідай своїми словами і **прив’язуй до цього проєкту**.

## Хмара загалом

**1. Регіон і AZ.** Регіон — географічна зона (напр. `eu-central-1`). AZ — ізольований ЦОД всередині регіону. Один сервер в одній AZ падає разом із зоною (пожежа, збій живлення). Multi-AZ / кілька інстансів у різних AZ підвищують доступність.

**2. IaaS / PaaS / SaaS.** IaaS — ви керуєте ОС і вище (EC2). PaaS — ви даєте код/контейнер, провайдер — рантайм (ECS Fargate, RDS частково). SaaS — готова програма (Gmail). У нас: **Fargate ≈ PaaS для контейнерів**, **RDS ≈ керована БД (PaaS)**, VPC/SG ближче до IaaS-рівня мережі.

**3. Shared responsibility.** Провайдер ніколи не відповідає за **ваш код, паролі, IAM-політики, які дані ви кладете в БД, чи вимкнули ви публічний доступ**. Фізична безпека ДЦ — на AWS; конфіг security groups — на вас.

**4. Vertical vs horizontal.** Vertical — більший інстанс. Horizontal — більше копій за балансувальником. Horizontal потребує **stateless** застосунку (стан у БД/кеші, не в пам’яті одного процесу). Наш API **stateless**: JWT + PostgreSQL.

**5. Pay-as-you-go / reserved / spot.** On-demand — гнучко для лаби. Reserved — знижка за зобов’язання. Spot — дешево, але можуть забрати. У схемі найдорожче зазвичай **NAT Gateway + ALB** (погодинно), не сам контейнер.

## Контейнери

**6. Контейнер vs VM.** VM — гіпервізор + своя ОС. Контейнер ділить ядро хоста, ізоляція через namespaces/cgroups. Спільне: ізольовані процеси, власна ФС з образу.

**7. Образ / контейнер / реєстр.** Образ — незмінний шаблон шарів. Контейнер — запущений екземпляр. Реєстр (ECR) — сховище образів. Незмінність дає відтворюваність деплою.

**8. Шари Dockerfile.** Кожна інструкція — шар. Спочатку `COPY package.json` + `npm install`, потім код: зміна коду не інвалідує кеш залежностей.

**9. Не `latest`.** `latest` пливе між збірками → невідтворювані деплої. `slim`/`alpine`/`bookworm` — варіанти дистрибутива (менший розмір / конкретний Debian).

**10. Дані не в контейнері.** Контейнер ефемерний. У нас: volume `pgdata` локально; у хмарі — **RDS**.

**11. DNS у Docker-мережі.** Сервіси резолвляться за іменем (`db` у compose). `localhost` у контейнері — сам контейнер, не хост і не сусід.

**12. Compose.** Описує кілька сервісів, мережу, volumes однією командою. `depends_on` чекає **старту** (або healthcheck у v2), але не гарантує готовність додатку до логіки без healthcheck.

## Мережа і безпека

**13. Public / private.** З інтернету видно лише **ALB**. ECS і RDS — у **private** subnet (вихід у інтернет через NAT для pull образів).

**14. Security group.** Stateful firewall на ENI. Правило «від SG застосунку» автоматично охоплює всі задачі сервісу, навіть коли їх IP змінюються; CIDR ноутбука крихкий і ширший ризик.

**15. Load balancer.** Розкидає HTTP по healthy targets; при падінні інстансу health check виводить його з пулу, трафік іде на живі.

**16. IAM.** User — довгоживуча людина/ключ; Role — тимчасові credentials через AssumeRole; Policy — дозволи. Least privilege: GitHub role лише ECR push + ECS update + PassRole на execution/task roles.

**17. Ролі vs ключі.** Ключі в Secrets можуть витекти й довгоживуть. Роль + OIDC видає короткоживучі токени під конкретний workflow run.

**18. Пароль БД.** Генерує Terraform (`random_password`), потрапляє в `DATABASE_URL` у task definition як env (не в git). Читає ECS task; у консолі видно тим, хто має права на ECS/TaskDefinition. (У проді краще Secrets Manager — можна згадати на захисті.)

**19. CDN.** Кеш статики ближче до користувача. Для JSON API з динамічними даними майже не потрібен; має сенс для Swagger UI/статики.

## Дані

**20. Managed DB.** Провайдер: патчі, бекапи, failover (якщо Multi-AZ), моніторинг хоста. Ви втрачаєте повний root/OS-доступ і частину кастомних розширень.

**21. Multi-AZ / PITR.** Multi-AZ — синхронна standby в іншій AZ. PITR — відкат за транзакційним логом. У лабі Multi-AZ вимкнено (дешевше); backup retention = 1 день — базовий PITR можливий у межах retention.

## CI/CD та IaC

**22. CI vs CD.** CI — збірка/тести на зміну коду. CD — автоматична доставка. У нас: checkout → OIDC → build/push → нова task def → update service.

**23. Тег = commit SHA.** Однозначна версія коду. Відкат: задеплоїти попередній SHA (оновити task definition на старий тег).

**24. OIDC.** GitHub видає JWT; AWS trust policy перевіряє `sub` (репо) і `aud`; STS дає тимчасові ключі. Немає довговічних ключів у GitHub Secrets.

**25. Консоль руками.** Немає історії, важко повторити, drift. IaC: версіонування, review, відтворюваність, `destroy`.

**26. Terraform.** `init` — провайдери/backend; `plan` — diff; `apply` — застосувати; `destroy` — знести. **State** — мапа ресурсів; у git не кладуть (секрети, конфлікти) — remote backend (S3) у проді.

**27. Порядок створення.** За графом залежностей (посилання на `.id` / `depends_on`): спочатку VPC/subnet, потім SG, RDS, ALB, далі ECS service що залежить від listener і DB.

**28. Drift.** Зміна в консолі → `plan` покаже різницю і захоче повернути до коду (або навпаки відобразить нове, якщо імпортовано). Тому все тільки через Terraform.
